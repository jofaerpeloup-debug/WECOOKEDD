## 2. Frozen product and data decisions

1. **One one-off reminder per dated entry.** Absence means off. A reminder is not a repeating weekly template, meal slot, automatic recommendation, Cook Mode timer, or NOTIF3 inbox producer. An unavailable recipe's entry remains eligible because the plan entry still exists; notification text uses generic plan wording and never fabricates recipe content.
2. **Explicit wall time and zone.** Persist exact 24-hour `HH:mm` and an accepted named IANA zone captured from the device on each explicit create/edit; show that zone before confirmation. Editing may retain the saved zone or explicitly recapture the current device zone. Reject offset-only IDs and unknown zones. `dateKey` is still the entry's calendar identity, interpreted for this reminder in the persisted zone. The server alone derives one UTC `fireAt`; a device-zone change never silently rewrites it. A move retains wall time and zone and resolves the destination date atomically. No automatic zone conversion is inferred from travel.
3. **DST, past time, and move policy.** Resolve a repeated wall minute to its earlier occurrence; reject a nonexistent minute on create/edit; reject create/edit if derived `fireAt <= server now`. An accepted move into a DST gap or `fireAt <= server now` keeps the moved entry but atomically sets reminder to `null` and advances its reminder revision. The response states the reminder was turned off. A duplicate, stale, or failed move changes neither entry nor reminder. An unavailable Recipe does not turn a valid reminder off. Server resolution uses the pinned `@js-temporal/polyfill` `0.5.1`: `Temporal.ZonedDateTime.from` with `disambiguation: 'earlier'`, then round-trip year/month/day/hour/minute equality to reject gaps, with a future check against the server clock. Validate named IANA zone IDs before resolution; no device `Date` or offset supplied by the client is authority.
4. **Visible state.** Distinguish `off`, `saved but device alerts unavailable`, `saved, awaiting device capacity`, `synchronization pending`, and `scheduled on this device`. Only a fresh validated OS inventory plus current eligible permission may justify the last state; iOS provisional/ephemeral status adds quiet/temporary wording. Saving a specification must not claim delivery. Denied permission, unsupported web runtime, OS schedule failure, capacity exhaustion, and missing current reconciliation leave server truth intact and show truthful retry/settings guidance.
5. **Preference and permission policy.** `preferences.notifications.reminders=false` suppresses and cancels this installation's meal alerts while retaining server reminder specifications; re-enable triggers reconciliation. `push=false` controls remote push only, and NOTIF1 `enabled` remains its compatibility mirror. Saving/editing a reminder is allowed when local OS permission is denied or unrequestable, but the UI says saved and unavailable and offers the platform settings/retry path. Android requires granted permission. On iOS, `AUTHORIZED` allows normal scheduling, `PROVISIONAL` allows quiet scheduling with explicit quiet copy, and `EPHEMERAL` allows temporary scheduling with explicit temporary copy; `DENIED`, `NOT_DETERMINED`, unknown or malformed status never certifies scheduling. Permission revocation cancels app-owned pending reminders where possible. A permission request occurs from an explicit user action, not silently during background reconciliation.
6. **Complete UTC horizon.** At each reconciliation capture one UTC `now`, then use the half-open `[now, now + 28 * 24 hours)` instant window. The existing 31-day list limit can cover every eligible `dateKey` only with a UTC-derived range: UTC calendar date of `now` minus **one** day through UTC calendar date of `now` plus **29** days, inclusive (31 keys). Accepted zones at a target instant must have an offset in `[-12h,+14h]`; reject a zone/time outside that bound. For UTC start day `D`, the earliest eligible local date is `D-1` at UTC−12 and the latest is `D+29` at UTC+14 near the window end. This covers device/saved-zone differences without using device-local today or the displayed week. Strictly validate the whole list, reject duplicate entry IDs, and filter using authoritative `fireAt`; a malformed/failed list leaves the prior OS inventory untouched. Reconcile at auth restore/sign-in, app foreground, planner focus, permission/preference change, and successful meal mutation. Beyond-window specifications stay saved; an unopened app has no refresh guarantee.
7. **Navigation target.** The OS payload is a routing hint only. A local tap waits for auth and navigation readiness, binds to the currently authenticated owner/session and tap operation, fetches the entry by ID under that session, compares the requested entry ID, owner discriminator, reminder revision and exact `fireAt`, and navigates to the entry's *current* week only if the reminder is still active and the response is complete. A genuinely delivered tap is eligible from the authoritative `fireAt` through exactly 24 elapsed hours afterward, using one captured comparison time after the fresh server read. A future or undelivered claim, a tap older than 24 hours, or a malformed instant is ineligible. The Meal Plan screen must select/highlight that entry after its own owner-scoped week fetch. A missing, changed, foreign, expired, malformed, offline, or superseded tap never navigates or marks an inbox row read. Cold-start taps cannot rely on an in-memory generation from the process that scheduled them; the persistent local session epoch defined in section 4 fences prior sessions.

## 4. Local scheduling, reconciliation, and security

- The server is authoritative for owner, entry, date, time, zone, instant, revision, preference, and session validity. The OS is a disposable projection. MEAL4 must supply a caller-chosen Expo request ID under its reserved versioned `wecooked.meal4.v1` namespace with a fresh high-entropy per-schedule nonce; Expo's API makes this input optional, but omitting it gives no independent malformed-payload ownership proof. Persist that exact ID in a small SecureStore ownership journal under a separate key from the session binding **before** calling `scheduleNotificationAsync`; if the journal write fails, do not schedule. Require the settled returned ID to equal the requested ID; a different or uncertain result is a schedule failure requiring operation-owned exact-ID compensation when possible and degraded status, not an inferred ownership mapping. Keep journal entries across logout, epoch rotation, and account switches until a fresh complete inventory proves the ID absent; a journal entry is provenance for exact-ID cleanup only, never a local schedule database, server authority, match, capacity count, or proof of delivery. Do not reconstruct missing entries from the namespace or payload. The journal proves which IDs this installation submitted under the app-controlled producer model; it is not an OS-enforced guarantee against a deliberately forged exact ID, so contradictory evidence always fails closed. Strict local data is exactly `{ version: 1, kind: 'mealPlanReminder', entryId, reminderRevision, fireAt, sessionEpoch }`. `sessionEpoch` is a random opaque local discriminator stored in SecureStore with the authenticated owner ID and current stable server `sessionId` from the access-token session binding. That binding is inspected only after authenticated restore/sign-in, never accepted as server authority, and the session ID is never put in OS content. Retain the epoch across process restarts and token refresh of the same session; rotate on a new login/session/account switch and clear on all local auth teardown paths. A missing/malformed/mismatched binding fails closed: rotate, reject old taps, enumerate and cancel old MEAL4 requests before scheduling. Never include account names, recipe titles, access/refresh tokens, raw routes, or provider IDs in OS content; title/body are generic.
- **Validate the entire scheduler inventory before acting.** `getAllScheduledNotificationsAsync()` must resolve to a complete array of request objects with distinct nonempty string `identifier`, object `content`, object `content.data` when present, and a present `trigger` property; do not interpret `null`, `undefined`, a singleton, duplicate IDs, or a partial array as an empty inventory. Inspect and classify **every** item before any mutation: valid foreign (no MEAL4 ID or payload discriminator; arbitrary other data and `trigger: null` allowed), valid MEAL4 (reserved ID, exact ID in the trusted write-ahead journal, exact strict payload, compatible non-null platform-specific one-off trigger), invalid provably MEAL4-owned (reserved ID with exact journal proof and no contradictory foreign discriminator, but malformed payload or trigger), or unknown/ambiguous (including missing/invalid ID, duplicate ID, malformed outer shape, any MEAL4 discriminator without journal proof, unreadable/malformed journal, or conflicting foreign payload). The namespace is an app convention, not an OS-enforced or cryptographic ownership guarantee; it alone cannot authorize recovery cancellation. Every namespaced MEAL4 request still requires a non-null compatible platform-specific one-off trigger for its `fireAt` to match or certify `scheduled on this device`. Invalid and ambiguous requests never match or certify a schedule. If any item is ambiguous or the inventory/journal is unavailable, do **zero** cancels and **zero** schedules. Strictly validate every returned server entry and preference before ordinary diffing; their failure likewise permits no OS mutation. Only a malformed OS request with verified exact-ID ownership may enter recovery after the independent complete server-horizon gate succeeds. Never call cancel-all.
- **Bounded malformed-inventory repair.** Only after a complete valid strict server horizon and complete OS inspection with unique IDs, a valid journal, and no ambiguous item may recovery cancel invalid provably MEAL4-owned requests, by their exact inventoried IDs, serially and in lexicographic ID order. Serialize recovery for this installation across concurrent reconciliation passes; one pass must retain exclusive ownership through its persistent count read, count write, cancellation, and verification, so another foreground, focus, startup, or auth-triggered pass cannot spend the same attempt slot. Check the captured owner/session generation, local session revision, epoch, and operation before each cancellation and after each await; an auth transition stops this pass. Never cancel a valid foreign request or use a prefix, guessed ID, payload field, or stale in-memory list as sole ownership proof. Stop on the first cancellation error or uncertain outcome. After any attempted repair, reread the **whole** OS inventory; ordinary diff/cancel/schedule may begin only after a fresh complete strict validation finds no invalid or ambiguous item and fresh server/preference/permission validation succeeds. A failed reread cannot certify repair or trigger a cleanup/scheduling pass. Retain journal entries until a fresh complete read proves them absent. Valid foreign requests, including null-trigger ones, remain untouched throughout.
- **Durable exact-ID recovery budget.** The ownership journal stores one non-negative safe-integer recovery-attempt count per exact ID, initially zero when that ID is first journaled; automatic and explicitly user-initiated manual recovery share this persisted count and the same exclusive, serialized recovery mechanism. After a complete strict inventory proves the invalid request's exact-ID MEAL4 ownership, hold that exclusive recovery pass through the persisted count read, count write, Expo cancellation, and verification. A missing, malformed, or unreadable count is an unavailable journal and authorizes no cancellation. Automatic recovery may cancel only while the existing durable count is below three. At count three or greater, only a genuine explicit user action may request one bounded manual recovery pass; foreground, focus, restart, auth restoration, or a queued retry never qualifies as that action. For **every automatic or manual recovery cancellation**, durably persist `count + 1` to that same journal record and await confirmed write success **before** calling Expo's exact-ID cancellation. If the increment cannot be represented safely, or persistence fails or is uncertain, invoke no Expo cancellation; a later pass must reread the persisted count and fail closed if it cannot establish the value. The reserved attempt is consumed even if the app crashes after the write and before or during cancellation, cancellation rejects or has an uncertain result, or cancellation resolves but a fresh strictly validated inventory still contains the invalid ID. Never decrement, reset, or replace a still-present ID's count because of a manual request, account switch, logout/logout-all, app restart, foreground/focus reconciliation, or a successful cancellation call alone. At count three or greater with that invalid ID still present, persist/derive the paused degraded state from the retained journal record, show `synchronization unavailable — manual retry/support needed`, and perform no further automatic repair or ordinary scheduling. A manual attempt increments the count beyond three and never clears or bypasses this automatic pause. Ambiguous ownership or an unavailable journal pauses immediately with the same observable state and no OS mutation. Each manual pass remains subject to the same exact-ID ownership classification, account/session fencing, serialization, cancellation-stop, and fresh whole-inventory reread gates as automatic recovery; it cannot clear the counter or re-enable automatic repair while the ID remains. Only a fresh complete strictly validated inventory proving the exact ID absent permits clearing its recovery counter and ownership record; if cleanup persistence fails, retain the conservative record and do not infer a schedule. Foreign and ambiguous requests are never recovery-cancelled.
- **Strict server list for the scheduler.** The current `getMealPlan` helper converts a missing `data.mealPlan` array to `[]` and fills malformed entry fields with `null`; MEAL4 reconciliation must not use that lossy result. In the allowlisted `mealPlanService.js`, expose a separate strict horizon read that rejects a missing/non-array `mealPlan`, an incomplete item, duplicate ID, invalid `id`/`recipeId`/`dateKey`/timestamps, out-of-request date, invalid `reminderRevision`, or a reminder lacking valid `localTime`, named zone, and canonical UTC `fireAt`. Require a complete public entry projection, including explicit `reminder: null` for off entries; do not coerce missing fields to null or suppress parse errors. Also require the current authenticated user's `preferences.notifications.reminders` to be an actual Boolean; neither `NotificationsContext`'s fallback defaults nor a malformed user payload authorizes a destructive diff. Treat any malformed/partial API success as unavailable for this whole pass: complete server-horizon validation precedes every OS-mutating reconciliation or malformed-inventory recovery attempt, and failure causes zero OS schedules, cancellations, recovery increments, mutation-related journal writes, or pruning. Resume journal-proven bounded recovery only after a separate complete valid server response. Preserve the separately contracted auth/teardown cleanup path. Leave valid OS schedules untouched and retry only after a fresh successful read. The ordinary planner list may retain its existing UI behavior until explicitly updated; it is not scheduler authority.
- **Bounded deterministic reconciliation.** Only after a clean full-inventory read (including after recovery), for one captured session and UTC horizon, sort eligible distinct entries by `(fireAt ascending, entryId ascending)`. Across Android and iOS cap total app pending requests considered by MEAL4 at **32**: capacity is `max(0, 32 - validated non-MEAL4 pending count)`, and select the first `capacity` entries. This is a conservative app budget, not a platform delivery guarantee. Entries beyond capacity remain saved and explicitly say awaiting device capacity; never silently replace them with later entries. Diff by entry ID, revision, instant, session epoch, and validated non-null platform-specific one-off trigger; keep exactly one matching request, choose duplicate keeper by lexicographically lowest OS ID, and cancel only journal-proven MEAL4 IDs proved stale/duplicate/excess. Cancel before scheduling to avoid oversubscription; process both phases in sorted order, serially. Stop on first OS error, re-enumerate if possible, record which entries are verified, and leave unverified entries as synchronization pending. Successful earlier cancels/schedules remain; next foreground/focus/retry reconciles them idempotently. Never roll back an authoritative server write because OS scheduling fails. A crash between schedule and bookkeeping is repaired from a freshly validated inventory; the ownership journal does not reconstruct schedule state.
